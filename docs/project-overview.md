# Project Overview — S.C.R.A.P.

_Generated by the document-project workflow (exhaustive scan), 2026-06-21._

## Purpose

S.C.R.A.P. is a **transaction-scoped document storage gateway** for billing ETL
workflows. Billing services write and read immutable Documents (XML, PDF, etc.)
through a gRPC API and retrieve them by `(transaction_id, document_name)` without
knowing whether bytes are served from local hot storage, peer replicas, or a
Backend object store (S3, GCS, Azure Blob).

It is **not** an S3-compatible API. It is a purpose-built gateway with strong
consistency guarantees: immutable-after-ACK Documents, transaction-scoped reads,
all-or-error verified reads, and Raft-backed metadata authority. The corpus may
reach billions of relatively small files (p50 ~16–128 KiB, max 128 MiB) with
7-year retention.

Read `CONTEXT.md` at the repo root before changing code — it is the canonical
glossary and process contract.

## Architecture at a Glance

- **Pattern:** Layered, service-oriented monolith. A composition root
  (`internal/cmd`) wires three network surfaces over a per-Shard storage engine.
- **Three network surfaces:**
  - **Public gRPC** (`DocumentService`) — client document write/head/read/find.
  - **Peer gRPC** (`PeerService`) — inter-Member byte replication, block
    transfer, consistency check, index rebuild, Raft forwarding.
  - **Admin HTTP** (`internal/admin`) — health, metrics, eviction/rewrap/
    quarantine operations, admin-gated pprof, test hooks.
- **Storage authority:** Raft metadata is the source of truth for Document
  visibility; the Pebble Projection is a rebuildable derived index. Document
  bytes never enter Raft (ADR 0001).
- **Durability path:** local Block bytes + Openlog → peer replication → Raft
  metadata commit → visible/ACK → async Backend upload.

## Phasing Status

The project is built in phases (see `CONTEXT.md`). Implemented surfaces span
through the production-security and multi-shard milestones:

- **Phase 1** — single-node spike-store contract (Block/Frame/.idx formats, API).
- **Phase 2a/2b** — Raft replication, peer byte transfer, leader-only reads,
  light/deep scrub, quarantine + auto-repair.
- **Phase 3** — Backend upload via Upload Outbox + admission pressure.
- **Phase 3.6** — OpenTelemetry evidence plane.
- **Phase 4** — partial eviction (followers evict `.blk`, retain `.idx`).
- **Phase 4.5** — production security bridge (mTLS, authz, audit, rate limit,
  OpenBao Transit envelope encryption, peer scope policy).
- **Phase 5** — restore-first cold reads (ADR 0027).
