# Async content scanning with ClamAV + YARA

Status: Accepted

Date: 2026-05-27

## Context

S.C.R.A.P. stores immutable billing documents (XML, PDF) for 7 years. Documents are
generated by trusted internal billing services, not uploaded by untrusted users. The
threat model is supply-chain compromise, lateral movement, or compromised upstream
service — not drive-by malware. Compliance and audit requirements motivate content
scanning even though the document source is trusted.

Documents are immutable after ACK: they cannot be modified, overwritten, or deleted.
This means a scanner can only quarantine, never remediate. The write path currently
ACKs at p50=11ms; inline scanning would add 100–500ms+ and create a hard dependency
on scanner availability.

Two quarantine concepts already exist or are needed:

- **Block Quarantine** (existing): filesystem rename of corrupt `.blk`/`.idx` files,
  triggered by deep scrub integrity failures. All documents in the block are affected.
- **Content Quarantine** (new): metadata-level gate on individual documents flagged as
  malicious. Block bytes are untouched; only the read path is gated.

## Decision

### Scan timing: async post-ACK

The content scanner runs asynchronously after documents are durably stored and visible.
It never participates in the write path. Scanner unavailability does not block writes.

Rejected: inline pre-ACK scanning. Latency cost is disproportionate (10–50x p50 write
latency). Scanner outage would block all writes. Immutability means inline rejection
is the only benefit — but async quarantine achieves the same protection with seconds
of additional exposure.

### Engine: ClamAV + YARA

ClamAV provides broad signature-based detection. YARA provides custom rules for
billing-domain threats (embedded JavaScript in PDFs, macro-laden XML, anomalous
document structure). Both run self-hosted with no document bytes leaving the
infrastructure.

Rejected: cloud multi-engine APIs (VirusTotal). Documents may be subject to audit or
subpoena; sending them to third-party scanning services creates data sovereignty risk.
Rejected: commercial SDKs (Sophos, ESET). Licensing cost per node, proprietary binary
in containers, and detection quality improvement is marginal for the trusted-source
threat model.

### Integration: sidecar clamd per pod

Each Member pod runs a `clamd` sidecar container. Communication via Unix socket.
Signatures kept in memory (~300–500 MB RAM per pod). Fault-isolated: a sidecar crash
stops scanning on that member only; writes continue.

ClamAV signatures updated via `freshclam` pulling from a private `cvdupdate` mirror
(no outbound internet from pods). YARA rules deployed via Kubernetes ConfigMap
(version-controlled, PR-reviewed).

### Module: separate `internal/avscan/`

Content scanning lives in `internal/avscan/`, separate from `internal/scrub/`. Deep
scrub verifies integrity (CRC/SHA-256); content scanning verifies safety (malware
signatures). Same block traversal pattern but different concerns, different scheduling,
different lifecycle.

Both share the I/O budget framework (token-bucket rate limiter + client-latency-aware
pause) to avoid starving client reads.

### Scan location: leader-only

Only the shard leader runs content scans. Block bytes are identical across replicas
(mirror layout, ADR 0003), so scanning on multiple members is redundant. When the
scanner flags a document, the leader proposes a `QuarantineDocument` Raft command;
all members apply the quarantine to their local projection.

Leadership change: the new leader resumes scanning from the persisted block-ID
watermark.

### Quarantine store: Pebble key prefix + Raft command

Content quarantine state is stored in a dedicated Pebble key prefix
(`q\x01<transaction_id>\x00<document_name>`). A `QuarantineDocument` Raft command
writes the entry on apply. This is a sparse index — empty when no infections exist.

The read path performs a Pebble point-get on the quarantine prefix before serving
bytes. Zero overhead when no documents are quarantined.

### Scan progress: dual watermark

The scanner tracks two watermarks in the projection:

1. `last_scanned_block_id` — tails sealed blocks for new-document scanning.
2. `last_sig_version_scanned` — when ClamAV signature version advances, the block
   watermark resets, triggering a full corpus re-scan at background priority.

No per-document scan state is stored. The watermark approach means the scanner may
re-scan some documents after a restart or leadership change — this is idempotent and
harmless.

### Read path behavior

- `ReadDocument`: returns `FAILED_PRECONDITION` with `reason: QUARANTINED_AV` for
  content-quarantined documents. No bytes served.
- `HeadDocument`: returns metadata including a `scan_status` field
  (`CLEAN`/`QUARANTINED`/`UNSCANNED`). Billing services can see the document exists
  for reconciliation.
- `FindDocuments`: includes content-quarantined documents in results with
  `scan_status` field. Transaction `doc_count` integrity is preserved.

### Admin operations: gRPC AdminService

Quarantine management (list, inspect, confirm, release) is exposed via a gRPC
`AdminService` on a separate admin port, NetworkPolicy-isolated from client traffic.
The AdminService is a general-purpose operator surface — future scrub control,
resharding, and other admin operations will share it. Confirm and release operations
propose Raft commands for cluster-wide consistency.

### Rescan behavior

When a signature update causes a re-scan hit on a previously-clean document, the
quarantine flow is identical to an initial scan hit. The `QuarantineDocument` Raft
command includes a `scan_type` field (`INITIAL`/`RESCAN`) for operational triage —
rescan hits on old documents have larger blast radius and may need different
incident response.

### Scan scheduling

A 30-second configurable ticker polls for new sealed blocks. Detection latency is
dominated by block seal time (64 MiB threshold), not poll interval. The ticker also
checks for signature version changes to trigger re-scan sweeps.

## Consequences

- Write path is unaffected. No latency or availability impact.
- ~300–500 MB additional RAM per pod for the clamd sidecar.
- A 4th network port (admin gRPC) is added to the pod spec.
- The `RaftCommand` oneof gains a `QuarantineDocument` variant.
- Proto messages gain `scan_status` fields (`HeadDocumentResponse`, `DocumentMeta`).
- A private ClamAV mirror (`cvdupdate`) is required infrastructure.
- Worst-case detection latency = block seal time + 30s poll + scan duration (~200ms
  per small document). For sustained writes sealing blocks every few seconds, typical
  detection is under 1 minute.
- False positives require operator intervention via AdminService to release.
