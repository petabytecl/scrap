# Story 6.4: `scrapctl` Release Evidence Bundle

Status: review

## Story

As a release owner,
I want `scrapctl` to collect release-relevant diagnostics and evidence,
so that V2 closure can be reviewed from reproducible operator output.

## Acceptance Criteria

1. **AC-6.4.1 - Release-relevant diagnostics are collected.** Given a prod-like Cell is running, when `scrapctl` evidence collection runs, then it gathers status, leaders, peers, upload pressure, faults, eviction/restore status, Shard health, scanner/quarantine status, OpenBao readiness, and redaction proof where implemented by feature epics. Evidence records command, environment, artifact path, and changed-boundary list.
2. **AC-6.4.1a - Bundle manifest is reviewable.** Given the evidence bundle is written, when its manifest is inspected, then it records artifact naming, checksums, provenance, command lines, environment, commit/ref, and redaction/privacy status. Evidence records the manifest schema and example.
3. **AC-6.4.2 - Bundle artifacts are leak-scanned.** Given evidence output is written, when artifacts are inspected, then raw identifiers, Backend keys, tokens, private keys, Document bytes, data keys, and wrapped-key ciphertext are absent. Evidence records stdout, stderr, report, and artifact leak-scan results.
4. **AC-6.4.3 - Missing evidence cannot silently pass.** Given a feature-specific evidence command is missing, when the bundle runs, then the result marks the missing evidence as `FAIL` or `CONCERNS` instead of omitting it. Evidence proves missing evidence cannot silently pass release closure.
5. **AC-6.4.4 - Epic 6 stays aggregation-only.** Given the bundle needs a feature-specific command, when that command is not implemented by the owning feature epic, then the bundle records the missing command and does not add replacement product behavior. Evidence proves Epic 6 stayed aggregation-only.

### Manifest and Privacy Design Guardrails

- Keep manifest artifacts bundle-relative. Local stdout may print the generated bundle path for the operator, but public evidence summaries should avoid host-absolute paths.
- Use SHA-256 for artifact digests. This aligns with existing repo checksum usage and general provenance practice; no new dependency is required.
- SLSA provenance guidance is useful context for `where/when/how produced`, source ref, build/run parameters, and subject digests, but this story must not claim SLSA compliance or introduce signing/attestation infrastructure unless separately chartered. [Source: `https://slsa.dev/spec/v1.2/build-provenance`; `https://slsa.dev/spec/v1.1/verifying-artifacts`; `https://slsa.dev/spec/v1.1/attestation-model`]
- If an artifact is intentionally unavailable because an owning feature epic did not implement a safe passive command, the manifest/evidence artifact should record `CONCERNS` or `FAIL` with owner and mitigation instead of silently omitting that domain.
- Do not add new runtime dependencies, assertion libraries, or external signing tools for Story 6.4. Use the Go standard library for hashing, walking files, JSON, and pattern checks unless a current repo package already provides a needed helper.

### Redaction and Security Notes

- Public docs, committed evidence, and tracker-ready summaries must not include credential values, private key material, generated certificate material, Document payloads, raw Document identifiers, Backend object keys, tokens, trace IDs, request IDs, auth claims, host-absolute paths, data keys, wrapped-key ciphertext, or raw dependency/log output.
- Keep scan patterns bracket-split in docs and evidence artifacts so the scan commands do not self-match.
- Negative privacy tests should use obvious fake shaped values that cannot be real credentials.
- Before commit, run the AGENTS security checklist. This story touches release evidence and CLI-adjacent code in the dev pass, so secret/raw-identifier leakage is a primary risk.
